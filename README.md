## Завдання 1: Дослідження HTTP Cookies

* **Що таке кука:** Це просто короткий текстовий рядок, який сервер просить браузер запам'ятати. Вони потрібні, щоб сайт впізнавав користувача (наприклад, тримав сесію чи пам'ятав кошик), бо сам протокол HTTP "забуває" все після кожного кліку.
* **Set-Cookie vs Cookie:** `Set-Cookie` прилітає від **сервера** (наказ браузеру створити куку). А заголовок `Cookie` надсилає вже сам **браузер** назад на сервер при кожному наступному переході.
* **Робота без браузера:** Куки працюють всюди, бо це звичайні HTTP-заголовки. Через консольну утиліту `curl` параметр `-c` записує отримані куки у текстовий файл, а `-b` читає їх звідти і додає до запиту.

## Завдання 2: Атрибути Cookies

| Атрибут | Що робить | Приклад |
| :--- | :--- | :--- |
| **Name=Value** | Ключ і значення куки | `sessionid=abc123` |
| **Domain** | Сайти, на які браузер буде відправляти цю куку | `example.com` |
| **Path** | Конкретна папка (урл) на сайті, де кука працює | `/api/v1` |
| **Expires** | Точна дата і час, коли кука видалиться | `Wed, 22 May 2027 10:00:00` |
| **Max-Age** | Скільки секунд жити куці з моменту створення | `3600` (1 година) |
| **HttpOnly** | Ховає куку від JavaScript (захист від крадіжки токенів хакерами) | Флаг |
| **Secure** | Дозволяє передавати куку тільки через безпечний HTTPS | Флаг |
| **SameSite** | Керує відправкою кук при переході з лівих сайтів (захист від CSRF) | `Lax`, `Strict`, `None` |

* **Session vs Persistent:** Сесійні живуть у пам'яті і зникають, як тільки закриєш вкладку. Постійні (`Persistent`) мають таймер життєдіяльності (`Max-Age`) і зберігаються на диску навіть після перезавантаження комп'ютера.
* **HttpOnly:** Повністю блокує доступ до куки через JS. Навіть якщо хакер запустить свій скрипт на сторінці, він не зможе витягнути куку через `document.cookie`.
* **Secure vs HttpOnly:** `Secure` захищає куку в дорозі (дозволяє передачу тільки по HTTPS), а `HttpOnly` захищає її вже всередині браузера (від злих скриптів).

## Завдання 3: Структура Set-Cookie заголовка

1. **Сесійна кука** (тільки HTTPS, без JS):  
   `Set-Cookie: sessionid=abc123; HttpOnly; Secure; SameSite=Strict`
2. **Постійна для всього домена** (на 30 днів):  
   `Set-Cookie: user_id=777; Domain=example.com; Path=/; Max-Age=2592000; SameSite=Lax`
3. **Тільки для шляху `/api`** (на 1 день):  
   `Set-Cookie: api_token=xyz987; Path=/api; Max-Age=86400; HttpOnly; Secure`
4. **Крос-сайт кука для аналітики** (на 1 рік, працює всюди):  
   `Set-Cookie: _analytics_id=track_123; Max-Age=31536000; SameSite=None; Secure`

* **Чи піде кука `Path=/api` на `/api/users`?** Так, піде. Браузер звіряє шлях за префіксом (початком рядка), а `/api/users` починається з `/api`.

## Завдання 5: HTTP Кешування

| Директива | Що робить |
| :--- | :--- |
| **max-age=N** | Браузер юзає локальний файл N секунд і взагалі не смикає мережу. |
| **no-cache** | Зберігати файл можна, але перед показом треба обов'язково перепитати у сервера через ETag, чи він не змінився. |
| **no-store** | Жорстка заборона кешу. Нічого не зберігати на диск, завжди качати заново (для банків та секретних даних). |
| **public** | Файл можуть кешувати всі підряд: браузер, провайдери, CDN-мережі. |
| **private** | Файл особистий, його дозволено зберігати тільки в браузері користувача. |
| **must-revalidate** | Коли час `max-age` закінчився, показувати стару копію заборонено — тільки новий запит на сервер. |

* **no-cache vs no-store:** `no-cache` дозволяє тримати файл на диску, але змушує перевіряти його свіжість на сервері. `no-store` взагалі забороняє будь-яке збереження.
* **Якщо ETag збігся:** Сервер повертає статус **304 Not Modified** (каже: "в тебе все свіже, читай з кешу").
* **Навіщо перевіряти ETag:** Це економить трафік. Коли час кешу вийшов, браузер шле ETag. Якщо файл на сервері той самий, сервер повертає коротку відповідь 304 без самого файлу, і сторінка відкривається миттєво.

## Завдання 6: HTTP Кешування з Conditional Requests на C#

Код виконання завдання лежить в окремому файлі `Task6_Cache.cs`.

* **Чому в 304 відповіді менший Content-Length:** Тому що при статусі `304` сервер не пересилає сам файл (тіло відповіді важить 0 байт), а шле тільки декілька рядків заголовків.
* **Використання кешу:** Браузер спочатку дивиться на `max-age`. Якщо час не вийшов — бере з диска. Якщо вийшов — надсилає умовний запит з `If-None-Match` (ETag) і, якщо отримує 304, продовжує показувати стару копію.

## Завдання 7: Cookies vs localStorage vs sessionStorage

| Характеристика | Cookies | localStorage | sessionStorage |
| :--- | :--- | :--- | :--- |
| **Розмір** | Дуже малий (~4 KB) | Великий (~5-10 MB) | Великий (~5-10 MB) |
| **Передача на сервер** | Автоматично летить з кожним запитом | Ніколи сама не передається | Ніколи сама не передається |
| **Час життя** | Задає сервер / до закриття | Вічно, поки сам не очистиш | До закриття поточної вкладки |
| **Доступ з JS** | Можна (якщо немає HttpOnly) | Повністю відкритий | Повністю відкритий |

* **Чому куки йдуть на сервер, а localStorage ні:** Куки створені для авторизації (сервер має знати, хто робить запит). `localStorage` — це суто локальна скриня для потреб фронтенду (зберегти тему, чернетку тексту), щоб не ганяти мегабайти мережею при кожному кліку.
* **Коли юзати localStorage:** Для великих несекретних налаштувань інтерфейсу (історія пошуку, збережений рівень гучності в плеєрі).
* **Де безпечніше зберігати sensitive дані:** Тільки в **Cookies з флагами `HttpOnly` та `Secure`**. Дані в `localStorage` повністю відкриті для JS, і якщо на сайті є XSS-вразливість, будь-який скрипт миттєво вкраде токени.

## Завдання 8: SameSite та CSRF атаки

* **Strict:** Кука шлеться тільки якщо ти вже сидиш на цьому сайті. Клікнеш на посилання з гугла — кука не відправиться (відкриєш сайт розлогіненим).
* **Lax:** Стандартний режим. Блокує куки для сторонніх скриптів та POST-форм, але додає куку, якщо користувач просто клікнув на звичайне GET-посилання.
* **None:** Куки шлються всюди без обмежень (потрібно для сторонніх віджетів та реклами). Працює тільки разом із флагом `Secure`.

* **Що таке CSRF:** Атака, коли шкідливий сайт підсовує тобі приховану форму, яка робить запит на твій банк (де ти залогінений). Браузер раніше автоматом чіпляв куки до всіх запитів, і банк думав, що це ти переказуєш гроші хакеру.
* **Чи діє SameSite для POST-запитів:** Так. Режими `Lax` та `Strict` повністю блокують передачу кук, якщо сторонній сайт намагається надіслати дані через POST-форму. Це практично повністю знищило проблему CSRF.
